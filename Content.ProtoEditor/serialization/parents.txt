# Prototype Inheritance

So some prototypes can inherit from multiple parents, taking their components/properties and having
them applied to the prototype.
How this works is a slight mystery because of how complex a lot of the code is, so a lot of splunking
to figure out what and how this works.

During PrototypeManager::ResolveResults, which is done after all the prototypes have been loaded,
we kick off a bunch of tasks for inheritance under PrototypeManager::PushKindInheritance.

In turn, this then looks over the tree of all the inherited prototype IDs, this is per Kind of entity,
so the EntityPrototype gets its own tree, LatheProperties another, etc.

All of this is then handled in PrototypeManager::PushKindInheritance::ProcessItem and is kicked off
for each root node in the graph.

I'm not sure but I think the root nodes are effectively prototypes with zero (concrete) parents.
This does mean that things like `ConveyerBeltAssembly` can totally be a child of `BaseItem`, but
because the latter is an abstract type it doesn't count as a "root" node.

This does make me question something though, how does the abstract there populate the node if its
not a root node?

This ProcessItem is recursive and starts from root nodes and goes to the children of that root node,
i.e. The prototypes that inherit from that particular node, and so on.

This means that we basically do no processing at the root node specifically, and only really do something
when we have a parent to pull from.

---

When processing the inheritance, we have a dictionary of results using `InheritancePushDatum`.
This is initially populated with details from the all the kinds, including abstract.
This answers the question I had before about how this works, the abstracts ARE root nodes in this
graph as well, they have to be.

In the example of SatiationIcons (a pretty simple and flat inheritance), both the `HungerIcon` and
`ThirstIcon` are root nodes,

So we populate these Results with the MappingData for each prototype we've encountered for that
particular kind.

If the child has multiple parents then we seem to basically just batch up the parent slightly,
I'll need to figure out which parent wins out but I'm assuming it's last one applies changes.
