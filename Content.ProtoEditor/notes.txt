# ProtoEditor

Intent is to be a decent looking application for managing prototypes and being able to see all the different
components, and default values, for a particular entity.

We can break this down into a set of functionality we would like to have, so we can more work on it over a long time.

## Plan

### Stage 1 - Loading Prototypes

The first step is to figure out how to load ALL the prototypes currently available in the codebase, and we can look
to the YAMLEditor project for inspiration since it does the same thing.
Albeit in a way that seems to be setup for "IntegrationTests" rather than anything that's more generalised.

Even if it's "IntegrationTest" related, it's likely to help us produce the right sort of list, so worst case
we can probably rely on it for the moment in this stage of figuring out what/how to get things to work.

### Stage 2 - Visualising Prototypes

Now we have a complete list of ALL the prototypes available across the codebase, we probably want to start showing it
to users.
The only question is "how" but this is the stage for figuring that out.
Alphabetical? Searching? Fuzzy finding? Broken down per file? Directory structure? Etc.

### Stage 3 - Editing Prototypes

Once we can see the prototypes, we should have the ability to alter the component data and then save it to disk.
Addition of components, should be doable as well.

- Add the file path to the IPrototype, maybe under certain conditions.

### Comments and You

If we were to naively just start writing the Yaml from memory to disk, we’d nuke all the comments and just have bare (but uni-formally formatted) text. Comments provide some load-bearing structure for forks to be able to turn remove components, override values but maintain their originals close by, and also just good anchor points for merge conflicts.

The most ideal prototype editor, in my eyes, would need to be able to handle keeping comments as-is, loading them into memory and dumping them out in the right places to maintain parity.

We might be able to work around it a little by having the yaml dumped out to temporary file, or even as a pop-up for the user to copy and paste into the actual file. Then they could take that and add/update any comments as required. Ultimately though that falls short of the “This is a cool prototype editor that handles things for me” goal in my head.

### Metadata

One problem is figuring out how to work with and store the metadata for a prototype and any inheritance that it has. Where the prototype came from is a somewhat easy solve, but then noting that Component A for this prototype comes from Parent A, which in turn inherited it from Parent B, is a bit more annoying to solve.

Reasoning for this being important is that we don’t, I imagine, want to have the whole object be stored directly as Yaml. We need to be able to ignore writing properties and fields where they are the default, as well as where they not directly specified in the child Yaml.
